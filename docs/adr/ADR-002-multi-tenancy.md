# ADR-002: عزل المستأجرين بـ school_id في قاعدة واحدة

- **الحالة:** مقبول — 2026-08-18
- **السياق:** بدائل العزل: قاعدة لكل مدرسة، Schema لكل مدرسة، أو صفوف مشتركة بمفتاح مستأجر. مئات المدارس المتوقعة تجعل إدارة قواعد/Schemas منفصلة مكلفة (Migrations × N).
- **القرار:** Shared DB / Shared Schema؛ كل جدول مدرسي يحمل `school_id` (FK إلزامي، غير قابل لـ NULL). الإنفاذ المتراكم: Middleware يثبت المدرسة الموثقة، كل endpoint يفلتر بـ`request.school`، PostgreSQL RLS يفشل إلى الإغلاق، وقيود triggers تمنع العلاقات الأجنبية العابرة للمدارس، مع اختبارات عزل إلزامية.
- **التبعات:** Migrations واحدة للجميع وتقارير منصة سهلة؛ المخاطرة الأساسية IDOR/استعلام غير محكوم لا تعتمد على مراجعة الكود وحدها، لأن RLS يحصر الصفوف على مستوى قاعدة البيانات.

## ملحق (تحديث 2026-09-11): PostgreSQL RLS مفعل

- **الموقف:** RLS = **Defense in Depth** فوق طبقات Django، وليس بديلًا عنها أبدًا — طبقة Django تبقى المصدر الأول للإنفاذ لأنها تحمل سياق الدور والعضوية الكامل.
- **التنفيذ:** migrations `operations.0002` و`operations.0004` تفعل وتفرض السياسات على جذر المدرسة وكل جداول البيانات المدرسية المباشرة والتابعة. السياسات fail-closed بذاتها لأي دور PostgreSQL غير مميز؛ غياب المدرسة يعني صفر صفوف لا كل الصفوف، ولا يعتمد الإنفاذ على خيار اتصال يرسله العميل.
- **السياق:** Middleware يضبط `app.current_school_id` بعد إعادة تحقق العضوية ويمسحه قبل/بعد كل طلب. مهام Celery تستخرج مدرسة سجل المهمة تحت bypass ضيق ثم تكمل داخل سياقها.
- **سلامة العلاقات:** migration `operations.0003` يفحص البيانات القائمة ويفشل إن وجد ربط عابر، ثم يضيف constraint triggers لكل FK بين نموذجين مدرسيين.
- **التشغيل:** لا يستخدم التطبيق transaction-mode connection pooling، لأنه لا يضمن ثبات إعداد الجلسة طوال الطلب. bypass لا يضبط إلا لمسار منصة مصرح أو مهمة صيانة صريحة؛ ويجب أن يكون دور قاعدة بيانات التطبيق `NOSUPERUSER NOBYPASSRLS`.
