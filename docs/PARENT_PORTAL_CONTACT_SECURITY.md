# حماية تواصل ولي الأمر وعزل البيانات

هذا المرجع يكمّل معمارية بوابة ولي الأمر. رقم التواصل المدرسي منفصل عن رقم الدخول العالمي؛ تعديل نور أو المدرسة لا ينشئ مستخدمًا ولا يمنح صلاحية ولا يغير `User.mobile`.

## التنفيذ

- `students.0007_guardian_contact_revision` يضيف إصدار بيانات التواصل.
- `parents.0002_contact_security_and_rls` يفرض RLS على جميع جداول البوابة، ويمنع العلاقات المدرسية العابرة، ويجعل PostgreSQL المسؤول الوحيد عن إصدار التواصل والتعليق وإبطال التفعيل ومراجعة التواصل والتدقيق والتنبيه العام داخل معاملة تحديث الطالب نفسها.
- المقارنة تطبع الجوال السعودي والأرقام العربية دون تغيير القيمة المخزنة في الكتابة المباشرة؛ يظل فحص صلاحية مستلم SMS مطابقًا للسلوك السابق. تغيير الصيغة والمسافات فقط لا يزيد الإصدار ولا يعلق العلاقة. تغير الاسم بعد تطبيع NFKC والمحارف الصفرية والمسافات وحالة الأحرف يعد تغييرًا جوهريًا يحتاج مراجعة.
- تغيير فعلي للجوال، مسحه، أو كتابة قيمة غير صالحة مباشرة يعلق العلاقات `ACTIVE` المرتبطة بالتواصل فقط. علاقة ولي آخر تحقق منها استقلالًا (`contact_bound=false`) تبقى مستقلة. عودة الرقم السابق لا تعيد التفعيل.
- نور يحتفظ بالجوال السابق عند ورود قيمة فارغة أو غير صالحة، كما كان سابقًا. الاعتماد يقفل الطالب ويضيف المصدر والفاعل وبصمات HMAC إلى سياق المعاملة. القيم الأصلية لا تدخل Audit.
- ترتيب أقفال الخدمات هو المدرسة `FOR KEY SHARE` ثم الطالب ثم العلاقة والطلب؛ يقبل قفل المدرسة مشاركة بقية أولياء الأمور ويمنع التعارض الدوري مع نور الذي يقفل المدرسة أولًا `FOR UPDATE`. تعديل الطالب اليدوي وAdmin يتبعان الترتيب نفسه لأن حارس التواصل يكتب سجلات مرتبطة بالمدرسة. لا تغيّر هذه الإضافة أقفال نور أو سياسة اعتماده.
- مسارات `save()` و`update()` و`bulk_update()` وSQL وDjango Admin تمر بالحارس نفسه. التحديث الأمني لا يعتمد على signal أو task لاحقة. عند rollback ترجع حالة الطالب والعلاقة والطلب والرمز والمراجعة والتنبيه معًا.
- الكتابة المباشرة التي لا تمر بسياق الخدمة تسجل المصدر `DATABASE` والإصدارات. لا يحتفظ PostgreSQL بمفتاح HMAC؛ يمكن أن تبقى حقول بصمات التواصل فارغة في هذه الحالة بدل تخزين الرقم أو بصمة غير محمية.
- `parents.0003_exact_family_identity_guards` يربط طلب الأسرة بالطالب والمستخدم المحددين في العلاقة، ويمنع خلط مرفق أو إنذار أو مستند أو حالة إرشادية أو تفعيل مع طالب آخر داخل المدرسة نفسها.
- `parents.0004_durable_contact_resolution` يحفظ سبب حل المراجعة وإثباته في حقول مستقلة، دون استبدال سبب التغيير أو إثباته الأولي. يتضمن التدقيق الفاعل والمصدر وأن القرار موثق فقط؛ تبقى النصوص الخاصة داخل السجل المدرسي المحمي ولا تدخل metadata التدقيق.

## المدرسة والحساب العالمي

واجهات `/api/v1/staff/parents/` تتيح للمدير والوكيل فقط تعديل التواصل بعد التحقق وتوثيق السبب، ومراجعة التعارض، وحظر مستلم ثبت عدم موثوقيته، وتسجيل طلب تغيير رقم الدخول العالمي. حل المراجعة لا يعيد اعتماد العلاقة تلقائيًا؛ إعادة الاعتماد عملية مستقلة بتوثيق جديد.

تغيير الجوال العالمي يبقى طلبًا `PENDING`، وتخزن قيمته مشفرة. لا توجد آلية SMS لتغيير الجوال أو استعادة الحساب في هذا الإصدار. PostgreSQL يمنع تغيير رقم حساب له علاقات ولي أمر، حتى عندما تكون العلاقات في مدارس أخرى أو معلقة. نموذج المستخدم في Admin يصبح الرقم فيه للقراءة لهذه الحسابات، وإدارة المنصة ترد بخطأ مراجعة واضح بدل تغيير الرقم.

لا يستطيع مدير المدرسة أو إدارة المنصة أو Django Admin إعادة ضبط كلمة مرور حساب له أي علاقة ولي أمر، حتى المعلقة أو الملغاة؛ تأكيد أثر الحساب المشترك ليس إثبات ملكية. يلزم إجراء عالمي مستقل معتمد لتوثيق الملكية، وهو غير منفذ في هذا الإصدار. فحص العضويات والعلاقات يتم بسياق المستخدم صاحب الحساب كي لا تخفي RLS ارتباطاته بمدارس أخرى. تغيير صاحب الحساب لكلمة مروره بعد إدخال الكلمة الحالية يبقى متاحاً؛ إعادة ضبط الموظف غير المرتبط بالبوابة تبقى وفق السياسة السابقة.

واجهة الطالب القديمة تحافظ على التوافق لغير المرتبطين بالبوابة؛ عند وجود علاقة مرتبطة بالتواصل يلزم سبب وبيانات تحقق للتغيير الفعلي. لا تتحول بيانات التواصل الجديدة إلى صلاحية وصول.

يعرض نموذج الطالب في Django Admin سبب التغيير وتأكيد التحقق وتوثيقه. التغيير الفعلي لسجل له علاقة مرتبطة بالتواصل يحتاج هذه البيانات؛ سجلات غير مستخدمي البوابة تحتفظ بسلوكها السابق. التنفيذ يعيد التحقق عند الحفظ ويحفظ المصدر والفاعل والسبب وبصمات HMAC، وتبقى حماية الكتابات الجماعية والمباشرة في PostgreSQL.

## الدمج والحذف

لا تنقل عملية دمج الطلاب علاقات ولي الأمر أو طلباته تلقائيًا. وجود علاقة في السجل المصدر يظهر مانعًا صريحًا في المعاينة. مراجعات التواصل التي لا تمنح وصولًا تبقى على السجل المصدر المؤرشف؛ لا تنتقل إلى الطالب المعتمد.

يسجل تطبيق البوابة طلباته ومرفقاته وعلاقاته ضمن سجل الحذف النهائي السابق. حذف مدرسة يحافظ على حساب موظف أصبح ولي أمر وله علاقة باقية بمدرسة أخرى. لا تُنفذ أي عملية حذف إنتاجية ضمن هذه الإضافة.

## Existing Absence SMS Regression Verification

لم تتغير استعلامات `candidate_absences()` و`eligible_absences()` أو القالب أو مصدر الرقم أو منع التكرار أو حالات إعادة المحاولة. استثناء المستلم هو حظر موثق للطالب والرقم المحددين فقط، ويطبق دفعة واحدة في المعاينة والطابور ثم يعاد فحصه في العامل. علاقة البوابة ليست شرط SMS. الفرق بين `FULL` واكتمال اليوم موثق في `SCHOOL_SMS.md`.

اختبارات `test_parent_sms_regression.py` تغطي Dreams وMsegat دون حساب بوابة، استمرار SMS بعد تعليق علاقة، استمرار إرسال طالب آخر عند حظر رقم الطالب المتأثر، وإعادة الفحص قبل المزود. نجحت الحالات الخمس ضمن تشغيل الخادم الكامل النهائي: 1184 اختباراً دون فشل أو تجاوز. لم تُرسل رسائل حقيقية.

## Existing Student Leave & Gate Workflow Verification

لم تتغير ملفات `student_leaves` أو خدمة `StudentGateRelease` أو صلاحيات الحارس. لا توجد واجهة استئذان في مسارات التواصل، ولا تصنع البوابة عضوية مدرسية. اختبارات الاستئذان والحارس السابقة جزء من مجموعة Regression المنسقة.

## الاختبارات والأدلة

`tests/test_parent_contact_security.py` يغطي الكتابة المباشرة والجماعية وAdmin والتطبيع والمسح والاسم والrollback واستقلال الأبناء والاعتماد القديم، وتحقق الهوية داخل المدرسة ورفض المعلم. اختبار العزل يبدل الدور إلى `NOSUPERUSER NOBYPASSRLS` ويتحقق من الفهرس الخاص بالمستخدم مع بقاء بيانات الطالب محجوبة خارج سياق المدرسة.

`tests/test_parent_http_rls.py` يختبر HTTP الفعلي بدور PostgreSQL دون تجاوز RLS، مع منع طالب ومستند ومرفق خاص في مدرسة أخرى. `tests/test_parent_noor_concurrency.py` يسابق اعتماد نور الفعلي وإعادة مراجعة العلاقة في اتصالين مستقلين، ويقيس الزمن ويتحقق من بقاء التعليق ومنع وصول ولي الأمر إلى التواصل القديم.

فحص Ruff للملفات الجديدة والمعدلة اكتمل. التشغيل المركز النهائي نجح في 115 حالة، ويشمل أدوار PostgreSQL الحقيقية دون تجاوز RLS والتزامن الفعلي مع نور. التشغيل الكامل داخل Docker نجح في 1184 حالة دون تجاوز، في 153.94 ثانية. فحوص الهجرات والتحقق من Django اكتملت محلياً. الأدلة والأوامر والقيود في [تقرير المرحلة F](PARENT_PORTAL_STAGE_F_REPORT.md)؛ لم يحدث نشر إنتاجي أو إرسال SMS حقيقي.
