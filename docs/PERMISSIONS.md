# مصفوفة الصلاحيات (RBAC)

> الإنفاذ على الـ Backend حصرًا (DRF Permission Classes + Service Layer). الواجهة تخفي ما لا يخص الدور لكنها ليست خط دفاع.
> كل صلاحية مدرسية مشروطة ضمنيًا بـ: عضوية فعالة في `active_school` + اشتراك المدرسة يسمح بالكتابة.

## الأدوار

| الدور | النطاق |
|---|---|
| `PLATFORM_ADMIN` | المنصة كلها — **بدون** وصول اعتيادي لبيانات الطلاب |
| `SCHOOL_MANAGER` | إدارة مدرسة كاملة |
| `VICE_PRINCIPAL` | تشغيل المواظبة اليومية |
| `COUNSELOR` | الإحالات والحالات الإرشادية |
| `TEACHER` | تحضير الفصول والإحالة فقط |

المستخدم قد يجمع أدوارًا في نفس المدرسة (مثل TEACHER + COUNSELOR) — الصلاحيات اتحاد الأدوار.

## قواعد إنفاذ إلزامية

1. **العضوية قبل الدور:** أي طلب مدرسي يتحقق أولًا من `SchoolMembership(user, active_school, is_active=True)` ثم من الدور. `school_id` من العميل لا يُستخدم أبدًا.
2. **صلاحيات على مستوى الكائن:** «جلسته هو»، «إحالاته»، «الموجه له» تُنفذ كـ Object-Level Permission في الـ Services، لا في الواجهة.
3. **مدير المنصة معزول عن الطلاب:** endpoints المنصة لا تُرجع أسماء طلاب أو هوياتهم؛ أي وصول استثنائي (دعم فني) خارج نطاق MVP ويتطلب تصميمًا لاحقًا (break-glass + Audit).
4. **إدارة المنصة:** `/api/v1/platform/*` تتطلب `is_platform_admin` ولا تعتمد على `SchoolMembership`.
5. **الاشتراك:** الطلبات الكتابية المدرسية تمر عبر `SchoolScopedAPIView` وتُمنع عندما يكون وضع الوصول ليس `FULL`.
6. **الاختبارات الإلزامية** (المرحلة 2 وما بعدها): معلم لا يعتمد عذرًا/يصدر إنذارًا/يعدل إعدادات؛ مرشد لا يغيّر حضورًا؛ عضو مدرسة A لا يقرأ B؛ متعدد المدارس لا تختلط بياناته.
7. **حدود الواجهة في المرحلة 17:** Platform Admin يوجه إلى console المنصة دون مدرسة
   نشطة. login/logout وتبديل المدرسة تمسح cache الواجهة، لكن كل قرار صلاحية أو
   مستأجر أو اشتراك يبقى خادميًا ولا يعتمد على route guard أو إخفاء menu.
