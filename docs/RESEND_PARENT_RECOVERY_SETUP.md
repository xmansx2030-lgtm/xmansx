# Resend — إعداد بريد استرداد ولي الأمر

تاريخ المراجعة: 2026-10-08. هذا الدليل خاص برسالتين فقط:
`RECOVERY_EMAIL_VERIFICATION` و`PASSWORD_RESET`.
لا يستخدم Resend للحضور أو الغياب أو الرسائل المدرسية أو التسويق، ولا يحل محل
Dreams أو Msegat. تسجيل الدخول يظل بالجوال وكلمة المرور، وتغيير الجوال العالمي
يظل معطلاً. التفاصيل الأمنية في
[معمارية الاسترداد بالبريد](PARENT_EMAIL_RECOVERY_ARCHITECTURE.md).

## حالة الإعداد الخارجي

الكود يدعم Resend REST مباشرة دون اعتماد جديد أو SMTP احتياطي. أثناء هذه المهمة
لا يُنشأ حساب مزود، ولا يُغيّر DNS، ولا يُضبط نطاق حقيقي، ولا يُرسل بريد فعلي.
نجاح المحاكاة أو قبول المزود لا يثبت وصول الرسالة إلى صندوق المستخدم.
الإرسال الخارجي يحتاج عنوان اختبار مصرحاً به ونطاقاً موثقاً ومرسلاً معتمداً
ومفتاحاً مستقلاً قبل فتح التسجيل العام.

## النطاق وعنوان المرسل

على مسؤول التشغيل المعتمد استخدام نطاق أو نطاق فرعي مخصص للاسترداد، وتطبيق
سجلات DNS التي تعرضها لوحة Resend ثم التحقق من حالة النطاق في اللوحة. راجع
[توثيق النطاقات الرسمي](https://resend.com/docs/dashboard/domains/introduction).
لا تنسخ قيماً افتراضية من هذا الملف إلى DNS الحقيقي، ولا تغيّر MX للبريد الوارد
الحالي دون مراجعة مالك النطاق. عنوان `RESEND_FROM_EMAIL` يجب أن يتبع النطاق
الموثق المعتمد؛ القيم المنتهية بـ`.invalid` أو`.test` أمثلة صناعية لا تستخدم للإرسال.

خصص مفتاحاً لهذه الخدمة فقط بصلاحية `sending_access`، ومقيداً بالنطاق المختار.
لا تستخدم مفتاح إدارة كامل للوصول إلى النطاقات أو الرسائل أو غيرها. خزّن السر
في Secret Store الخاص ببيئة التشغيل، خارج Git وDocker image وواجهة المتصفح.
المزود يسمح بعزل المفاتيح وتقييدها بنطاق؛ راجع
[إدارة مفاتيح Resend](https://resend.com/docs/dashboard/api-keys/introduction) و
[إنشاء المفتاح وصلاحياته](https://resend.com/docs/api-reference/api-keys/create-api-key).

## متغيرات البيئة

| المتغير | الافتراضي أو القيمة المطلوبة |
| --- | --- |
| `PARENT_RECOVERY_EMAIL_ENABLED` | `false`؛ يفعّل بعد تجهيز التشغيل والتحقق المصرح به |
| `PARENT_RECOVERY_EMAIL_ADAPTER` | `resend` في التشغيل الحقيقي |
| `RESEND_API_KEY` | مفتاح سرّي مستقل؛ لا قيمة حقيقية في المصدر |
| `RESEND_FROM_EMAIL` | مرسل معتمد ضمن النطاق الموثق |
| `RESEND_TIMEOUT_SECONDS` | `10`؛ إعداد الإنتاج يقبل 1–30 ثانية |
| `PARENT_RECOVERY_VERIFY_TTL_SECONDS` | `86400`؛ الإنتاج يقبل 300–86400 ثانية |
| `PARENT_RECOVERY_RESET_TTL_SECONDS` | `900`؛ الإنتاج يقبل 60–900 ثانية |
| `PARENT_PORTAL_BASE_URL` | أصل HTTPS معتمد دون credentials أو query أو fragment أو مسار إضافي |
| `PARENT_RECOVERY_SYNTHETIC_EMAIL_ROOT` | صندوق خاص للمحاكاة فقط، لا يستخدم في الإنتاج |

مثال أسماء المتغيرات دون مفاتيح فعلية:

```dotenv
PARENT_RECOVERY_EMAIL_ENABLED=false
PARENT_RECOVERY_EMAIL_ADAPTER=resend
RESEND_API_KEY=
RESEND_FROM_EMAIL=
RESEND_TIMEOUT_SECONDS=10
PARENT_RECOVERY_VERIFY_TTL_SECONDS=86400
PARENT_RECOVERY_RESET_TTL_SECONDS=900
```

إعدادات الإنتاج تفشل عند تفعيل Resend دون مفتاح ومرسل صحيح وأصل HTTPS.
البنية الصحيحة للمرسل لا تثبت أن نطاقه موثق لدى المزود؛ فحص لوحة المزود
واختبار التشغيل المصرح به لازمان. لا ترفع TTL لاستيعاب فشل الإرسال، ولا تطبع
المتغيرات السرية عند تشخيص المشكلة. حافظ على مفاتيح التشفير وHMAC الحالية؛
تدويرها له خطة منسقة مستقلة عن تدوير مفتاح Resend.

## مسار الإرسال

المهمة `parents.send_recovery_email` تحمل UUID محاولة الإرسال فقط. توليد الرمز
يحدث داخل ذاكرة العامل؛ قاعدة البيانات تحفظ بصمته فقط. قبل الاتصال، يعيد العامل
التحقق من الحساب والبريد وإصداره وكلمة المرور والجوال والأهلية، ويحافظ على
ترتيب القفل `User → AccountRecoveryEmail → Delivery` أثناء الإرسال والإتمام.
لا يمرر العامل البريد أو الرابط أو الرمز الخام عبر Redis أو وسيطات Celery.

الطلب HTTPS ثابت إلى `https://api.resend.com/emails` ويحمل `Authorization` و
`Idempotency-Key` مساوي UUID المحاولة. لا تتبع التحويلات، ولا تستخدم proxy
من متغيرات العملية. المحتوى عربي HTML ونصي، بمستلم واحد ودون CC/BCC أو بيانات
طالب أو مدرسة. حد الطلب 16KiB وحد قراءة الرد 4096 بايت، مع TLS موثق وtimeout
قابل للضبط. العقد موثق في
[واجهة إرسال Resend](https://resend.com/docs/api-reference/emails/send-email).

روابط التحقق والاسترداد تستخدم fragment:
`/parent/verify-email#token=…` و`/reset-password#token=…`.
زيارة GET لا تعتمد البريد ولا تعيد تعيين كلمة المرور. لا تضف click tracking أو
open tracking أو إعادة كتابة الروابط لهذه الرسائل في لوحة المزود، ولا analytics
أو scripts خارجية إلى صفحات الرموز. لا تستخدم روابط الرموز في أدوات الدعم.

## حالات التسليم وإعادة المحاولة

| الحالة | المعنى والإجراء |
| --- | --- |
| `PENDING` | محاولة محفوظة لم يرسلها العامل بعد |
| `SENDING` | ادعاء مقفل لمحاولة واحدة؛ المهمة المكررة لا ترسل ثانية |
| `SUBMITTED_TO_PROVIDER` | استجابة نجاح مع UUID مرجعي؛ ليست إثبات وصول أو قراءة |
| `FAILED` | رفض محدد أو إعداد غير صالح؛ الرمز غير قابل للاستخدام |
| `UNKNOWN` | timeout/network/5xx أو رد نجاح تالف أو idempotency409؛ قد يكون المزود استلم الطلب |
| `CANCELLED` | تغيّر الحالة أو الأهلية قبل الإرسال؛ لا اتصال بالمزود |

لا توجد إعادة محاولة تلقائية أو حلقة مباشرة عند429. المحاولة التي بقيت `SENDING`
أكثر من عشر دقائق تصبح `UNKNOWN` عندما تصل مهمة أخرى لنفس UUID؛ ليست مهمة
صيانة دورية تدّعي تنفيذ استعادة تلقائية. إعادة الإرسال الصريحة خاضعة للحدود
وتنشئ محاولة جديدة وتبطل الروابط السابقة المتأثرة، ولا تعيد استعمال الحمولة
السرية القديمة. قد تصل الرسالة القديمة متأخرة لكن رمزها الملغى يفشل بأمان.

يحفظ Resend مفتاح idempotency لمدة24 ساعة. هذا دعم إضافي لمنع التكرار، وليس
بديلاً عن الحالة المقفلة في قاعدة البيانات؛ لا يعاد إرسال نفس المحاولة بعد
انتهاء نافذة المزود. HTTP409 قد يعني طلباً مطابقاً ما زال قيد التنفيذ، لذلك
يصنف التطبيق409 بصورة محافظة `UNKNOWN` دون قراءة جسم الخطأ. راجع
[دلالات idempotency الرسمية](https://resend.com/docs/dashboard/emails/idempotency-keys).

لا توجد Webhooks في الإصدار الأول. لا تعادل `SUBMITTED_TO_PROVIDER` حالة
`DELIVERED`، ولا يعتبر فتح البريد إثبات ملكية؛ الإثبات هو POST صريح صحيح بالرمز.

## Staging الصناعي

استخدم بيئة loopback الصناعية الموجودة فقط؛ إعداد
`config.settings.parent_staging` يسمح بـ`synthetic-file` دون مفتاح Resend.
المحول يرفض عنواناً خارج نطاق`.invalid` ويرفض أصلاً خارج localhost، ويرفض
الإنتاج وlocal غير المقيد. لا يوجد اتصال خارجي أو SMTP احتياطي.

الصندوق في mount مستقل:
`/var/lib/xmansx-parent-staging/email-outbox`.
الدليل0700 والملفات0600، والاسم UUID فقط. هذه ملفات رسائل وهمية تحتوي روابط
صناعية لتطبيق الاختبارات، وليست قاعدة بيانات رموز إنتاجية. لا تعرضها في Nginx
ولا API ولا logs ولا artifacts عامة، ولا تضفها إلى Git أو نسخ الطلاب الخاصة.
بعد انتهاء دورة الاختبار، احذف رسائل المحاكاة وفق إجراء محلي محدد بعد التحقق
من المسار وملكيته؛ لا تمسح volumes أو قواعد المستخدم تلقائياً.

pytest يحاكي بروتوكول HTTPS دون شبكة خارجية. Playwright يقرأ الصندوق الخاص
بأداة صناعية محددة، ويكمل العملية عبر صفحات التطبيق وPOST الحقيقي. النجاح
هنا يثبت التكامل المحلي، ولا يثبت تشغيل نطاق Resend أو وصول صندوق خارجي.

## اختبار إرسال فعلي لاحق — يتطلب تصريحاً محدداً

1. وثّق البيئة الصناعية والمرسل والنطاق والمزود وعنوان بريد اختبار يملكه
   المختبر، والتصريح برسالة تحقق واحدة ورسالة استرداد واحدة.
2. تحقق من migrations وRLS وأصل HTTPS وCSRF وSecure Cookies وRedis والعامل
   وحدود الإرسال، وأن التسجيل العام ما زال مغلقاً أثناء الاختبار.
3. أدخل المفتاح من Secret Store، وحدّث إعداد العامل والتطبيق بصورة منسقة.
   لا تنفذ `curl` برمز خام أو مفتاح في terminal/history لتجاوز الخدمة.
4. نفذ تسجيل ولي أمر صناعي وموافقة المدرسة وتفعيل SMS وفق المسار التجريبي
   المعتمد، ثم توثيق البريد برسالة واحدة عبر التطبيق. أثبت وصول الرسالة في
   صندوق الاختبار وسلامة POST الصريح، دون نسخ الرابط إلى التقرير.
5. اطلب استرداداً واحداً، وافحص UUID المزود وحالة اللوحة والوصول الفعلي، ثم
   كلمة مرور جديدة وبطلان الجلسات والرمز والكلمة القديمة وبقاء العلاقات.
6. كرر مهمة UUID نفسها وتحقق من عدم إرسال رسالة إضافية. لا تعيد إرسال
   `UNKNOWN` بغرض التشخيص؛ افحص مرجع المزود دون كشف الرابط أو البريد الكامل.
7. أوقف الاختبار فور إرسال غير متوقع أو كشف رمز أو خلل عزل أو فشل مستلم؛
   عطّل الميزة، أوقف المعالجة الجديدة وأبطل المحاولات المتأثرة عبر خدمة معتمدة.
   احتفظ بضوابط كلمات المرور المركزية والحسابات العالمية عند forward fix.

هذا الدليل لا يمنح تصريح إرسال؛ ولم يُنفذ هذا الاختبار الخارجي في المهمة.

## المراقبة وإدارة الأخطاء وتدوير المفتاح

راقب الأعداد والمعدلات حسب الغرض والحالة وأكواد الخطأ المحدودة، وعمر `PENDING`
و`SENDING` وتراكم queue. اجعل التنبيه على429 و401/403 وارتفاع`UNKNOWN` مستقلاً
عن أنظمة SMS. لا تسجل recipient أو subject/body أو reset link أو rawtoken
أو Authorization، ولا تحمّل تقرير Sentry بجسم provider exception.

في dashboard المصرح به، راجع حالة UUID المزود للتشخيص دون تصدير أجسام الرسائل
أو روابطها إلى أدوات الدعم. لا تُطلِق حالة نجاح واجهة المستخدم بناء على مجرد
قبول المزود، ولا تعد رسالة استرداد لكل طلب مجهول لتجنب تعداد الحسابات.

لتدوير المفتاح: أنشئ مفتاح إرسال مقيداً بديلاً ضمن إجراء تشغيل مصرح به، حدّث
Secret Store للتطبيق والعامل، أعد تشغيلهما من الإصدار المثبت، نفذ smoke مصرحاً
به، ثم ألغِ المفتاح القديم بعد اكتمال التحقق. لا تسجل قيمة أي مفتاح في Audit
أو shell. إذا اشتُبه بتسرب، عطّل الإرسال وألغِ السر المتأثر ضمن مسار الحوادث؛
لا تخفض RLS ولا تعيد فتح reset الإداري القديم لإبقاء الخدمة عاملة.
