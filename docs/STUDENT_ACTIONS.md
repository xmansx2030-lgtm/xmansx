# الإجراءات الطلابية (المرحلة 12)

`StudentAction` سجل إداري لما **فُعل** تجاه الطالب. الفصل الصلب بين ثلاثة مفاهيم:

| النموذج | يجيب عن | مثال |
|---|---|---|
| `StudentWarning` (م11) | ماذا **استحق** الطالب | بلغ الإنذار الثاني |
| `StudentAction` (م12) | ماذا **فعلت** الإدارة | تم التواصل مع ولي الأمر |
| `GeneratedDocument` (م12) | ماذا **صدر وطُبع** | مستند الإنذار الثاني |

الإجراء لا يعدّل أي مصدر: `AttendanceMark` و`DailyAttendanceSummary` و`AbsenceExcuse`
و`StudentWarning` و`SchoolArrival` تبقى كما هي — تسجيل فقط.

## أنواع الإجراءات

| القيمة | العربية |
|---|---|
| `PARENT_CONTACT` | التواصل مع ولي الأمر |
| `STUDENT_MEETING` | مقابلة الطالب |
| `PARENT_MEETING` | مقابلة ولي الأمر |
| `COMMITMENT_TAKEN` | أخذ تعهد |
| `WARNING_DELIVERED` | تسليم إنذار |
| `ADMINISTRATIVE_NOTE` | ملاحظة إدارية |
| `REFERRED_TO_COUNSELOR` | إحالة إلى المرشد الطلابي (يُسجَّل تلقائيًا — م13) |
| `OTHER` | إجراء آخر |

القيم المخزنة إنجليزية ثابتة (Enum)؛ العربية للعرض فقط. القائمة كافية لـMVP فلم
يُنشأ نموذج `StudentActionTemplate` (لا نموذج بلا استخدام) — إضافته لاحقًا لتخصيص
كل مدرسة لا تكسر البيانات لأن النوع حقل مستقل.

## الحالة والإلغاء

`COMPLETED` أو `CANCELLED` فقط — لا Workflow معقد بلا حاجة. الخطأ يعالج بالإلغاء
مع `cancelled_by_membership` و`cancelled_at` و`cancellation_reason`، **ولا حذف
نهائي**. الإلغاء مرتين يرد `STUDENT_ACTION_ALREADY_CANCELLED` (409). قيد قاعدة
بيانات يمنع صف «ملغى» بلا وقت إلغاء.

## ربط الإنذار

`warning` اختياري (`null` للإجراءات المستقلة كمقابلة ولي أمر). إن أُرسل فيتحقق
الخادم أنه لنفس المدرسة **ونفس الطالب**، وإلا `INVALID_ACTION_WARNING_LINK` (400) —
نفس الرمز لإنذار مدرسة أخرى حتى لا يكشف وجوده. سلسلة نموذجية:

```
Warning LEVEL_2 → PARENT_CONTACT → COMMITMENT_TAKEN → WARNING_DELIVERED
```

**تسليم الإنذار قرار بشري**: إصدار الإنذار (م11) لا يعني تسليمه؛ التسليم إجراء
مستقل يسجله المستخدم.

## الملاحظات

`notes` ≤ 500 حرفًا لسياق مختصر، وليست مصدر الحقيقة لنوع الإجراء (النوع حقل مستقل).
تُهرَّب تلقائيًا عند دخولها أي مستند.

## الصلاحيات

| الدور | قراءة | إنشاء | إلغاء |
|---|---|---|---|
| مدير المدرسة | ✅ | ✅ | ✅ |
| الوكيل | ✅ | ✅ | ✅ |
| المرشد | ✅ | ❌ | ❌ |
| المعلم | ❌ | ❌ | ❌ |

المدرسة من `request.school` حصرًا؛ أي طالب/إجراء من مدرسة أخرى ⇒ 404.

## الواجهات

```
GET  /api/v1/student-actions/?student=&action_type=&status=&warning=
POST /api/v1/student-actions/
GET  /api/v1/student-actions/{id}/
POST /api/v1/student-actions/{id}/cancel/
```

القوائم مرقّمة، و`select_related` يمنع N+1 (استعلام واحد لصفحة كاملة — مقيس).

## التدقيق والحذف النهائي

`STUDENT_ACTION_CREATED` و`STUDENT_ACTION_CANCELLED` بمعرفات وأنواع فقط: لا نص
الملاحظة ولا اسم الطالب. الحذف النهائي: خطوة «الإجراءات الطلابية» في `PURGE_STEPS`
تُحذف **قبل** الإنذارات (‏`action.warning` بـPROTECT) وبعد المستندات.

## واجهة المستخدم

تبويب «الإجراءات» في ملف الطالب: التاريخ والنوع ومن نفّذه والإنذار المرتبط
والملاحظة والحالة، مع «إضافة إجراء» و«إلغاء الإجراء» حسب الصلاحية. التعهد ينشئ
إجراء `COMMITMENT_TAKEN` تلقائيًا **بعد** جاهزية المستند
(‏[GENERATED_DOCUMENTS.md](GENERATED_DOCUMENTS.md)).

## التكامل مع الإحالات (م13)

إحالة **إدارية** (وكيل/مدير) تسجل `REFERRED_TO_COUNSELOR` تلقائيًا داخل **نفس
معاملة** إنشاء الإحالة: إما ينجحان معًا أو لا شيء (رفض التكرار لا يترك إجراءً
يتيمًا). إحالة **المعلم لا تنتج إجراءً إداريًا**: سجلها هو الإحالة نفسها، ونسبة
إجراء إداري إليه تشويه للسجل. وإن كانت الإحالة مرتبطة بإنذار فالإجراء يحمل نفس
الإنذار — ولا يختلط بإجراء «تسليم إنذار» المنفصل.

**مصدر الحقيقة يبقى `StudentReferral`**: الإجراء أثر إداري في الخط الزمني، وتغيير
حالة الحالة (استلام/إغلاق) يقرأ من الإحالة لا من الإجراء.

## جاهزية المرحلة 13

سجل الإجراءات كامل زمنيًا لكل طالب، وتستهلكه الإحالة للمرشد (م13) دليلًا على ما
جُرِّب قبلها — وقد تحقق فعليًا بعد الدمج: السلسلة إنذار ← مستند ← تسليم ← إحالة
تظهر كلها في تبويب الإجراءات بترتيبها.
